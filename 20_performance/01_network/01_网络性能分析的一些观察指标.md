# 网络性能分析的一些观察指标

> 参考文档:[Linux 内核 mlx5 ethtool counters 文档](https://www.kernel.org/doc/html/v6.15/networking/device_drivers/ethernet/mellanox/mlx5/counters.html)


## 1. 物理网卡层面

如下介绍的观察指标是基于`mlx5`网卡：
```bash
# ethtool -i eth20
driver: mlx5_core
version: 25.10-1.7.1
firmware-version: 20.39.3004 (MT_0000000224)
expansion-rom-version: 
bus-info: 0000:4b:00.0
supports-statistics: yes
supports-test: yes
supports-eeprom-access: no
supports-register-dump: no
supports-priv-flags: yes
```

### 1.1 相关观察指标

1） **观察是否存在物理网卡接收丢包**

  ```bash
  # watch -n 1 'ethtool -S eth20 | grep rx_discards_phy; ethtool -S eth21 | grep rx_discards_phy'
  ```

2）**观察是否存在物理网卡发送丢包**

```bash
# watch -n 1 'ethtool -S eth20 | grep tx_discards_phy; ethtool -S eth21 | grep tx_discards_phy'
```

3）**观测buffer相关**

```bash
# ethtool -S eth20 | grep buffer
     rx_out_of_buffer: 317261837
     rx_oversize_pkts_buffer: 0
     rx_buffer_passed_thres_phy: 0
```
下面介绍一下相关字段的含义:

|              字段             |                                             含义                                                         | 
|------------------------------|----------------------------------------------------------------------------------------------------------|
| `rx_out_of_buffer`           | 数据包到达 RX Queue 时，没有可用的软件接收 buffer/WQE，网卡无法接收，通常会造成丢包。不是 socket 接收缓冲区不足。      |
| `rx_oversize_pkts_buffer`    | 到达接收队列的数据包长度超过驱动为其分配的接收 buffer 大小，数据包因此被丢弃。可能涉及网卡 MTU 与软件 buffer 大小不匹配。 | 
| `rx_buffer_passed_thres_phy` | 物理端口内部接收缓冲区使用量超过 **85%** 的事件次数，反映网卡端口出现过拥塞/积压。它本身不等于丢包数。                   | 

三个 buffer 的区别：
- rx_out_of_buffer：主机 RX Queue 没有可供网卡 DMA 写入的接收缓冲区。
- rx_oversize_pkts_buffer：单个报文比所分配的接收缓冲区更大。
- rx_buffer_passed_thres_phy：网卡物理端口内部缓冲区占用超过阈值。

重点是判断`rx_out_of_buffer`是否仍在增加:

```bash
# watch -n 1 "ethtool -S eth20 | grep -E 'rx_out_of_buffer|rx_oversize_pkts_buffer|rx_buffer_passed_thres_phy'"
```
如果它持续快速增长，说明正在发生接收侧丢包，常见原因包括 RX Ring 太小、RX 队列分布不均、CPU/软中断处理不及时，或驱动无法及时补充接收 buffer。继续检查：

```bash
# ethtool -i eth20
# ethtool -g eth20
# ethtool -l eth20
# ethtool -x eth20
# ethtool -S eth20 | grep -Ei 'rx[0-9]+_|alloc|drop|miss|discard|out_of_buffer'
# cat /proc/interrupts | grep -iE 'eth20|mlx'
```

4） **观察rx_buff_alloc_err**

```bash
# ethtool -S eth20 | grep -E rx_buff_alloc_err
```
`rx_buff_alloc_err`表示：驱动在为 RX Ring 分配接收数据所需的内存 buffer（或 SKB）时失败的次数。

造成`rx_buff_alloc_err`增加的常见原因有：

- 系统内存紧张或内存碎片化
- NUMA 节点本地内存不足
- 驱动/page pool 无法及时获得内存页
- RX Ring 很大，或高流量下 buffer 回收不及时

5）**观察tx_queue_dropped**

```bash
# ethtool -S eth20 | grep tx_queue_dropped
```

`tx_queue_dropped` 在 mlx5 驱动中的含义是：发送数据包时发生 DMA 映射失败，导致数据包被驱动丢弃的数量。

也就是:
```text
内核准备发送 SKB
      ↓
驱动尝试将数据映射给网卡 DMA
      ↓
DMA 映射失败
      ↓
丢包，tx_queue_dropped 增加
```
它通常不是因为链路拥塞，也不等同于 qdisc 队列满。常见原因包括：
- DMA/IOMMU 资源不足或异常
- 内存压力
- 驱动或固件问题
- PCIe/IOMMU 配置问题
- 发送 buffer 资源不足

6）**观察rx_steer_missed_packets**

```bash
# ethtool -S eth20 | grep rx_steer_missed_packets
```

`rx_steer_missed_packets`表示：网卡已经收到数据包，但该包没有匹配到硬件 Flow Steering 流表中的任何规则，因此被网卡丢弃。

路径如下：

```bash
报文到达网卡
    ↓
进入 mlx5 硬件流表匹配
    ↓
没有匹配规则或默认转发规则
    ↓
网卡直接丢弃
    ↓
rx_steer_missed_packets 增加
```

这里的 steer 是 mlx5 硬件流量导向/流表匹配，不是 RX Ring buffer，也不单纯表示 RSS 分配不均。

常见场景：
- SR-IOV、VF、representor 或 switchdev 模式
- Open vSwitch/TC flower 硬件卸载
- 修改硬件流表时存在短暂规则空窗
- 流表规则配置错误、缺少默认 miss 规则
- 报文的 VLAN、MAC、隧道等字段与现有规则不匹配
- 驱动、固件或卸载规则异常

### 1.2 总结

针对物理网卡层面我们可以使用如下命令综合性观察:

```bash
# watch -n 1 'ethtool -S eth20 | grep -E "discards_phy|rx_out_of_buffer|rx_buffer_passed_thres_phy|rx_buff_alloc_err"' 
```

## 2. TCP协议层面

### 2.1 观察TCP的丢包与重传

#### 2.1.1 全机TCP丢包和重传

使用如下命令进行实时观察:

```bash
# sar -n TCP,ETCP 1
Linux 5.15.0-144-generic (host-172-31-16-99) 	11/23/26 	_x86_64_	(112 CPU)

22:43:30     active/s passive/s    iseg/s    oseg/s
22:43:31        76.00      1.00   1984.00   2182.00

22:43:30     atmptf/s  estres/s retrans/s isegerr/s   orsts/s
22:43:31        73.00      0.00      0.00      0.00     80.00
```
重点字段：
- iseg/s：每秒接收 TCP segment 数。
- oseg/s：每秒发送 TCP segment 数。
- retrseg/s：每秒重传 segment 数。
- isegerr/s：接收到的错误 TCP segment。
- estres/s：已建立连接异常复位数。
- orsts/s：发送 RST 数。

可以粗略计算：
```text
TCP重传率 ≈ retrseg/s ÷ oseg/s × 100%
```
这只是趋势指标；重传也可能由乱序、ACK 延迟、RTO 或对端异常引起，不一定都是物理网络丢包。

要查看内核累计计数，可以使用如下命令：
```bash
# nstat -az | grep -E \
'Tcp(InSegs|OutSegs|RetransSegs|InErrs|OutRsts)|TcpExt(TCPTimeouts|TCPSynRetrans)'
TcpInSegs                       548016867677       0.0
TcpOutSegs                      2952060168044      0.0
TcpRetransSegs                  1404174494         0.0
TcpInErrs                       6047               0.0
TcpOutRsts                      2229334362         0.0
TcpExtTCPTimeouts               2820623            0.0
TcpExtTCPSynRetrans             444557             0.0
```
重点是观察一段时间内的增量，而不是只看启动以来的绝对值。

#### 2.1.2 单条 TCP 连接

例如观察本地或远端 443 端口：

```bash
# watch -n 1 "ss -tinmep '( sport = :443 or dport = :443 )'"
```

按目标地址过滤：
```bash
# watch -n 1 "ss -tinmep dst 10.0.0.10:443"
```

1）**ss命令相关参数介绍**

- `sport = :443`：本机端口是 443，通常是服务端连接。
- `dport = :443`：对端端口是 443，通常是本机作为客户端访问 HTTPS。
- `-t`：TCP。
- `-i`：TCP 内部信息，如 RTT、拥塞窗口和重传。
- `-n`：不解析域名和服务名。
- `-m`：socket 内存和收发缓存。
- `-e`：扩展信息。
- `-p`：进程信息，可能需要 root 权限

2）**输出字段含义**

```bash
# ss -tinmep sport = :8081
State                        Recv-Q                        Send-Q                                                Local Address:Port                                                 Peer Address:Port                         Process                                                                                                                                                                                                                       
ESTAB                        0                             156                                                   172.31.16.120:8081                                                 172.31.16.98:50200                         timer:(on,204ms,0) ino:751764768 sk:346c2 cgroup:/system.slice/nginx.service <->
	 skmem:(r0,rb199928,t1436,tb87040,f6756,w1436,o0,bl0,d0) ts sack cubic wscale:12,13 rto:204 rtt:0.093/0.051 ato:40 mss:1448 pmtu:1500 rcvmss:1448 advmss:1448 cwnd:10 bytes_sent:48048 bytes_acked:47892 bytes_received:1301608 segs_out:616 segs_in:927 data_segs_out:308 data_segs_in:924 send 1245591398bps pacing_rate 2487838920bps delivery_rate 503652168bps delivered:308 app_limited busy:24ms unacked:1 rcv_rtt:1 rcv_space:21130 rcv_ssthresh:98940 minrtt:0.023
```
主要字段:

| 字段 | 含义 |
|---|---|
| `Recv-Q` | 已经收到、但应用程序还没读取的有效载荷字节数 |
| `Send-Q` | 已发送或等待发送、但尚未被对端确认的数据量 |
| `retrans:x/y` | 当前重传状态/累计重传次数，具体显示形式与内核和 iproute2 版本有关 |
| `bytes_retrans` | 累计重传字节数 |
| `lost` | 当前被 TCP 标记为丢失、尚未恢复的 segment |
| `unacked` | 已发出但尚未确认的 segment |
| `notsent` | 已进入 TCP 发送队列、但尚未真正发送的数据字节数 |
| `rtt` | 平滑 RTT 和波动值 |
| `rto` | 重传超时时间 |
| `cwnd` | 拥塞窗口 |
| `snd_wnd` | 对端当前通告给本机的发送窗口 |
| `rwnd_limited` | 发送受对端接收窗口限制的时间 |
| `sndbuf_limited` | 发送受本机发送缓存限制的时间 |

判断方向：
- bytes_retrans、累计 retrans 持续增加：连接发生重传。
- lost 持续非零：当前仍有未恢复的丢失数据。
- rwnd_limited 比例很高：对端接收窗口限制发送。
- sndbuf_limited 比例很高：本机发送缓存可能偏小。
- Send-Q 长期很大且 snd_wnd 很小或为零：对端接收慢或对端接收缓存不足。
- Recv-Q 长期很大：本机应用程序读取太慢，或本机接收缓存存在压力。

### 2.2 当前收发缓存占用容量

`ss -m`会显示:
```text
skmem:(r8192,rb262144,t0,tb4194304,f4096,w65536,o0,bl0,d0)
```
下面介绍一下里面各字段含义:

|   字段  |              含义                      |
|--------|----------------------------------------|
| `r`    | 当前接收方向占用的 socket 内存，包含管理开销 |
| `rb`   | 当前套接字允许的接收缓存总量                |
| `t`    | 已经交给三层发送、仍由 socket 统计的发送内存 |
| `tb`   | 当前套接字允许的发送缓存总量                |
| `w`    | TCP 已排队、尚未交给三层发送的内存          |
| `f`    | socket 预先分配但尚未使用的缓存            |
| `bl`   | socket backlog 占用                     |
| `d`    | socket 层记录的丢包数                    |

需要注意：
- Recv-Q 更接近“应用尚未读取的有效数据量”。
- r 是内核内存占用，包含 SKB 等开销，通常不等于 Recv-Q。
- Send-Q 不等于“尚未发送”；它也包含已发送但尚未确认的数据。
- 真正尚未发出的数据重点看 notsent 和 skmem 中的 w。
- rb、tb 分别是当前连接接收、发送缓存上限。

### 2.3 判断接收缓存是否过小

观察 TCP 内存压力和接收队列丢包：

```bash
watch -n 1 "nstat -az | grep -E \
'TcpExt(PruneCalled|RcvPruned|OfoPruned|TCPRcvQDrop|TCPBacklogDrop|TCPMemoryPressures|TCPToZeroWindowAdv|TCPFromZeroWindowAdv)'"
```
重点指标：
- TCPRcvQDrop：TCP 接收队列因内存/空间问题丢包。
- PruneCalled：内核尝试回收 TCP 接收队列内存。
- OfoPruned：因内存压力丢弃乱序队列中的数据。
- RcvPruned：接收队列内存回收仍无法满足限制。
- TCPMemoryPressures：TCP 子系统进入内存压力状态。
- TCPBacklogDrop：socket backlog 无法容纳更多数据。
- TCPToZeroWindowAdv：本机向对端通告零接收窗口。

如果这些计数持续增长，同时某连接：

```text
Recv-Q 长期很大
r 接近 rb
应用读取不及时
```
则说明接收端确实存在压力。但应先检查应用读取速度；单纯增大缓存可能只是把丢包变成更长的排队延迟。
