# 两种VIP高可用实现方式对比

我们有如下两种VIP 高可用/负载均衡的实现方式:

- 传统方式：把 VIP 直接配在物理网卡上，通常配合 keepalived/VRRP，靠 ARP 让交换机把流量送到持有 VIP 的那台机器。

- GoBGP 方式：VIP 通常配在 lo 或 dummy 接口上，由 GoBGP 向上游路由器通告一条到该 VIP 的 /32 或 /128 路由，由路由器决定把流量转发到哪台机器。

>ps: GoBGP 本身不是 VIP 方案，它只是一个 BGP 实现。真正干活的是“用 BGP 宣告 VIP 路由”这套架构。

## 1. 核心差异

|维度	    |传统VIP绑物理网卡	   |GoBGP 宣告 VIP                      |
|:--------|:-------------------|:----------------------------------|
|工作层级  |	L2	               |L3                                 |
|VIP 位置	|物理网卡	           |通常 lo/dummy                       |
|流量引导	|ARP，交换机转发	     |上游路由器按 BGP 路由转发              |
|典型高可用 |VRRP + keepalived   |BGP 撤销路由 + 收敛                  |
|典型模式   |主备，备机闲置	       | 多活，可 ECMP                       |
|网络依赖	| 同二层，ARP 可达	   | 上游支持 BGP                        |
|跨子网	  | 困难	               | 容易(更适合跨机架、三层网络)           |
|故障切换	|秒级，依赖 ARP 更新    |亚秒到秒级，BFD 可毫秒级              |
|负载均衡	|通常没有	            |ECMP 逐流分摊                       |
|配置复杂度	| 低	                |高                                 |
|安全风险	|ARP 欺骗、IP 冲突	    |路由泄露、劫持                       |
|扩容	    |通常需要切换 VIP 所有者	|新节点宣告相同 VIP 即可加入            |
|状态连接	|单主模式比较稳定	      |路径变化可能影响有状态连接              |
|运维难度	|故障域较简单	          |要同时排查 BGP RIB、交换机 FIB 和服务器 |


## 2. GoBGP方案的优点

1) **摆脱 L2 依赖**

    VIP 不需要和客户端同网段，不需要 ARP，跨机架、跨子网、跨机房都能用。现代 Spine-Leaf 都是 L3，BGP 更契合。
  
    传统 VIP 切换依赖：
    - ARP/NDP
    - Gratuitous ARP
    - 交换机 MAC 表
    - 同一个二层广播域
    如果交换机、操作系统或安全设备没有及时接受 GARP，流量可能继续发往旧节点。
    
    GoBGP 通过撤销和发布路由完成切换，不依赖客户端刷新 ARP，适合纯三层 Leaf-Spine 网络。


2) **天然多活和 ECMP**
   
    多台机器同时通告同一个 VIP，上游路由器做 ECMP，流量分摊到多台。传统 VIP 通常主备，备机长期闲置。

3) **可以跨机架部署**
   
    传统方式通常要求 VIP 与服务器处于同一子网，或者要求网络提供较复杂的二层延伸。
    
    GoBGP 可以让不同机架中的服务器分别向各自的 ToR 交换机发布同一个 /32：
    ```text
    机架A服务器 → ToR-A ─┐
                       ├─ VIP/32
    机架B服务器 → ToR-B ─┘
    ```
    因此更适合大规模数据中心。

4) **扩缩容方便**
   
- 新增节点时
  ```bash
  gobgp global rib add 10.20.0.100/32
  ```
  节点就可以加入 ECMP。

- 摘除节点时
  ```bash
  gobgp global rib del 10.20.0.100/32
  ```
  上游重新计算路由，不再向该节点发送新流量。

5) **可与服务健康状态联动**
    理想流程是：
    ```text
    服务健康
      → 发布 VIP/32
    服务异常
      → 撤销 VIP/32
    ```
    相比仅检测服务器是否存活，可以做到服务级故障隔离

6) **收敛更快、可调**
   
    BGP 配合 BFD 能做到毫秒级故障检测和切换。VRRP 依赖 ARP 和主备切换，通常秒级，客户端 ARP 缓存还可能更慢。

7) **流量工程能力强**
   
    可以用 LOCAL_PREF、MED、AS_PATH、BGP 社区等控制入口流量，做权重、亲和、灰度、就近接入。

8) **适合 Anycast 和容灾**

   同一 VIP 在多地宣告，用户被路由到最近节点，天然抗 DDoS、抗单点故障。

10) **无 ARP 冲突和广播问题**
    
    不依赖免费 ARP，避免 ARP 欺骗、IP 冲突、VRRP 组播异常等问题。

11) **优雅下线**

    维护前先撤销路由或调整属性，让流量先切走，再停服务，做到不丢连接。

12) **云原生生态成熟**

    MetalLB、Calico、Cilium 等都用 BGP 宣告 VIP/Service IP，K8s 裸金属场景很常见。

## 3. GoBGP 方案的缺点
1) **依赖上游网络支持 BGP**

    需要路由器/交换机配置 BGP 邻居、AS 号、前缀策略。没有网络权限就玩不转。

2) **复杂度高**
   
    要管理 BGP 会话、AS、路由策略、前缀过滤、最大前缀、认证等。排障要同时看应用、主机路由、BGP 状态、上游路由表。

    部署时通常需要协调:
   
      - 服务器和交换机的 ASN
      - BGP 邻居
      - Import/Export Policy
      - 最大前缀数
      - ECMP 数量
      - BFD
      - 路由过滤
      - Community
      - 下一跳可达性
        
    错误发布一个大网段，例如把 /32 写成 /16，可能吸走大量不属于该服务的流量。

    建议交换机严格限制服务器只能宣告授权的 VIP：
    ```text
    只允许：10.20.0.100/32
    拒绝：其他所有前缀
    ```
    同时设置 maximum-prefix。

4) **GoBGP 本身不管健康检查**
   
    GoBGP 只负责 BGP。服务是否健康、什么时候该通告、什么时候该撤销，需要额外的 agent 或脚本。传统 keepalived 自带健康检查和 VRRP 状态机。

5) **安全风险更大**

    路由泄露或错误通告可能影响整个网络。必须严格做前缀过滤、TCP MD5/GTSM、RPKI 等。

6) **非对称路由问题**
   
    ECMP 或多路径可能导致去回路径不一致，有状态防火墙、NAT、连接跟踪容易出问题。

7) **ECMP 哈希可能不均**
   
    逐流哈希，大象流可能压到同一条路径。需要调整哈希策略。

8) **回包源地址问题**

    VIP 不在物理网卡上时，服务器回包源 IP 可能是物理网卡 IP。需要策略路由或额外配置，否则客户端可能拒绝。传统 VIP 绑网卡，源地址天然就是 VIP。

9) **不适合依赖 L2 的场景**
   
    需要广播、多播、同子网 ARP 的场景，BGP 替代不了。

11) **故障域变化**
    
    如果 BGP 会话全断，VIP 可能不可达。需要设计冗余邻居、多上游。

12) **有状态连接可能受影响**
    
    ECMP 通常按五元组哈希，所以同一 TCP 流正常情况下会固定到一台服务器。
    
    但当节点退出时：
    ```text
    ECMP成员变化
      → 一部分流重新哈希
      → 已建立连接可能到达另一台服务器
      → 新服务器没有原连接状态
      → TCP连接中断
    ```
    因此 GoBGP 多活更适合：
      - 无状态服务
      - 后端共享状态
      - 使用一致性哈希
      - 能接受连接重建的业务
        
    对于强状态服务，可以仍然只让当前 Active 节点发布 VIP。

13) **排障链路更长**
    
    传统方式主要检查：
    ```bash
    ip addr
    ip neigh
    arping
    ```
    GoBGP 方式需要逐层检查：
    ```text
    服务健康状态
      → GoBGP Global RIB
      → GoBGP Adj-RIB-Out
      → BGP邻居接收路由
      → 交换机RIB
      → 交换机FIB/ECMP
      → 服务器本地路由和监听状态
    ```
    例如：
    ```bash
    gobgp global rib "$vip/32"
    gobgp neighbor
    gobgp neighbor <peer> adj-out
    ip route get "$vip"
    ss -lnt
    ```

## 4. GoBGP 自身的特点

- 纯 Go 实现，易集成、易自动化，提供 gRPC API。

- 性能不错，支持 BFD、ECMP、路由策略、流规范等。

- 但它不是 keepalived 的替代品。它不做 VRRP，也不自带 VIP 健康检查。

- 常见组合：GoBGP + 健康检查脚本 + 上游路由器；或 MetalLB/Calico 内置 BGP 模式。

## 5. 怎么选

- 小规模、同二层、没有 BGP 权限、追求简单：传统 VIP + keepalived。

- 大规模、跨子网、多活、需要 ECMP、上游支持 BGP：GoBGP / MetalLB / Calico。

- K8s 裸金属 LoadBalancer：BGP 是主流方案。

- 只是主备高可用，网络团队不支持 BGP：别硬上 GoBGP，维护成本远高于收益。

**一句话总结**：传统 VIP 绑网卡是 L2 主备思路，简单但扩展性差；GoBGP 宣告 VIP 是 L3 多活思路，灵活、可扩展、能 ECMP，但依赖网络、复杂度高，且必须自己解决健康检查和回包源地址问题。
